n=128 历史实验分析与后续顺序（2026-10-22，Asia/Shanghai）

结论：有历史在线记录，但没有完成的 n=128 秘密恢复或 Slicer 对照结果。两种重量各一个独立密钥、两个 pattern、两组耦合的 (beta,s)，共八次 trial 全部在预处理阶段超时，候选为零；真实 Slicer 内核启动次数为零。不能写成“Slicer 成功率 0/8”，也不能据此判断算法无效。本次只做离线评估和算术分析，新增在线试验为零。

原计划每次总预算 45 秒；子进程超时线 42.9 秒。前一重量每次实测约 44.91 秒，监督程序最终强杀，结果文件仍停留在约 1.6 秒时的 running/lll_setup 检查点；它不是仍在运行。后一重量每次约 43.02–43.13 秒，保存了 interrupted/bkz_setup 状态。八次均没有完成 BKZ，更没有建筛库或实际提交 Slicer 目标。

本次独立评估的 8/8 份 trial 完整性核查通过，候选数为零、可比较的完整 trial 数为零；产物审计 passed=true、issues=[]。完整性通过只表示现存证据自洽。第一阶段 135 个保留文件及本次跟踪的原始数据/源码/报告 324 个文件均未变更。原 summary.json 的 evaluation_failed 表示原全量离线评估曾超时，不是本次选定范围评估失败；原文件保持不变。

时间瓶颈有直接证据。对 (12,24)，LLL setup 为 24.77–25.45 秒；LLL 行扫描操作为 11.11–12.34 秒；LLL Babai 操作为 2.46–2.58 秒。BKZ 到 worker 第 40.52–41.72 秒才开始，随即在约第 42.6 秒收到中止。检查点仅 0.260–0.280 秒，不到总时间的 1%；不能沿用早期 n=64 v1 的日志瓶颈解释。行扫描对 250 行的正负号共 500 个向量先做精确格成员、系数乘基重构，再判断残差半径，存在可避免的工作；现有计时不能把全部行扫描时间精确归为验证开销。

保存的 80 个 guesses 覆盖上述全部非零真值 tail，但实际调用覆盖为零。两个 pattern 的旋转计数不可直接相加；独立评估按实例取并集后，非零 tail 兼容旋转数分别为 58、82。

令 S=P∪T，|S|=6。每个非零系数至多排除六个旋转，所以零 tail 的有符号秘密代表至少为 2 max(0,n-6w_f)，两组分别至少 160、112 个。这说明零 tail 的非零短向量基线仍很重要，但不保证 LLL 能找到它们。后一重量四个保存的 LLL 基，其最短行平方范数均为 66049=q²，远高于秘密平方范数 36；LLL 行扫描和 Babai 完整运行后均未恢复。与 n=64 首级重量相比，n=128 的这一实例不再表现为 LLL 已经直接解出的区间；是否适合 Slicer 仍取决于尚未完成的 BKZ 与解码阶段。前一重量没有完成 LLL，不能据超时比较两种重量的总体难度。

建议按以下顺序推进；这些是后续方案，本次没有执行。

1. 先做低成本准备：补评已有 n=64 较高重量的完整记录，检查 Slicer 与基线的精确候选集合及等价类，不按候选数量判断相同；同时以保存的基核查“先精确残差排除、再完整验证”的输出等价性，增加约减、行扫描、Babai、建库、投影、内核、公开验证的分段计时。统一实现版本，不把已截断历史记录覆盖或改记为重试成功。其目的分别是确认已有增量证据、减少后续无效开销。

2. 做两次有界 n=128 pilot，先 (12,24)，后 (8,16)。保留已有公开实例、固定 p0、k=2、kappa=4、beta=20、s=32，逐次完整运行 direct-tail、LLL/BKZ rows 与 Babai、仅初始投影/回填的诊断、真实随机 Slicer。建议从每次 180 秒硬上限开始并明确记录阶段删失；此上限是探索方案，不保证足够完成。前一重量优先，因为历史已完成 LLL 且基线未解出。验收须有完整基线和真实内核 start/finish、全部 80 个目标的调用证据；若仍在约减超时，应先诊断该阶段，不扫描更多筛维。只有探索完成后才冻结后续确认实验；不能把这里复用旧密钥的结果当作新的独立样本。

3. 在能完整运行的参数区间隔离 pattern 的贡献。首先比较 k=0 与 k=2，共同 kappa=4，并显式冻结相同 T、backend seed、尾猜测列表、beta、s、预算；只复用相同 solver seed 不足以保证配对，因为改变 k 会改变随机数消费。维数分别 252、250。另加 k=kappa=0 的 256 维原始格，以及 k=2、kappa=0 的 254 维 pattern-only 行向量/SVP 基线，可分辨 pattern 与 tail 的收益。零 tail 对应零 CVP target，不能用返回零向量的 Babai 代替非零短向量基线。所有比较按完整恢复一个密钥的成本计算，包含无效 pattern 与尾猜测。

4. 根据 pilot 选择困难区间并逐项调参。若 BKZ rows/Babai 已全部恢复，则保留该结果作为容易区间，探索 (w_f,w_g)=(16,32)、(24,48)，而不是先增加随机迭代。若两者与 Slicer 均失败，先在固定 s=32 时比较 beta=20、25、30 的约减成本与效果；若基线未恢复而 Slicer 能恢复，优先保留该区间。随后在固定同一 BKZ 基时比较 s=32、40，并比较“逐目标解码”与“80 目标批量解码”，计入实际预处理、建库复用和整个攻击成本。避免同时改变 beta 与 s 后把差异归因于其中一个。

5. 对选定参数做统一版本的独立重复。预先冻结至少 10 个新 keygen seeds，每个密钥固定多个求解 seeds，所有方法按同一密钥配对。报告密钥级恢复率及区间、完整恢复时间、峰值内存、实际目标覆盖、超时所在阶段，以及 Slicer 相对基线新增的密钥恢复。旋转、正负号、多 pattern 和多求解 seeds 都不是新的独立密钥。只有这一阶段才适合对优势作统计结论。

当前最优先的新在线工作是第 2 步的完整分阶段 pilot。直接扩到 n=256、增加 pattern 数或提高 Slicer 迭代上限，都没有解决现有 n=128 尚未进入解码阶段的问题。
