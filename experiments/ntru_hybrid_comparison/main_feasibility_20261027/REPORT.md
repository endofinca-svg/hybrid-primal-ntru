# 同一 n=128 公钥上的首次 B/E/D 可行性对照

本轮已按 **B → E → D** 顺序各运行一次，全部在线实验结束，没有追加网格或增加预算。**B 成功；E、D 均未观察到成功，第二个 pattern 在约化阶段超时。** D 的正常 BDGL 预处理和 Slicer 调用确实执行，但本次没有获得额外有效解。

这是一把已有公钥上的一次固定配置可行性对照，不是统计意义上的加速结论。数据没有排除失败、超时或重试。本轮来自用户明确授权的主实例运行，不再作为只准备配置的阶段 2E。

## 公钥与历史记录

三组读取同一个原始文件 `experiments/ntru_compare_n128_w12_w24_q97/public/instance_01.json`，没有生成或挑选新公钥。全部 5 个实际 worker 记录的公钥文件摘要一致：

```text
public SHA256:  8e2e7cd27fdbd595d58a4baefb5326a4b04d05d0804962395ab9f74b26146bc7
h list SHA256:  f8063d5ac8396eaf262bf70c199ac5c961ec7b3f26343565234221d99d6c8d7c
```

参数实际为 n=128、q=97、商环 `Z_97[x]/(x^128+1)`，公开关系 `h*f=g`，重量为总非零数 `(12,24)`，目标范数平方 36。真实 h 有 128 项、127 项非零，系数范围 0..96；不是 h=1。[public_snapshot.json](public_snapshot.json) 保留了实际公开输入，[history_evidence.json](history_evidence.json) 给出原 summary、config、events、command 和 frozen manifest 的绑定证据。

历史 k=40 的 286.524902 秒来自同一公钥的唯一成功 pattern；该命令本身为 286.497795 秒，另有组开销。历史实际轨迹是 LLL 后从 β30 渐进到 β32，每块两轮，成功在 β32 第二轮；原配置 β 上限 216 没有在该成功记录中执行。本轮冻结**这段完整成功前缀**，没有把 cold β32 冒充历史配置，也没有把旧上限 216 全跑完才检查基行。

## 冻结配置与成本边界

共同约化：MPFR192、proved LLL、delta=0.99、eta=0.51，随后 β30 两轮 → β31 两轮 → β32 两轮。每轮是一次显式 `BKZReduction.tour` 调用，clean 不跳过下一轮，auto_abort=false；seed=10001，线程数 1，策略来自当前固定 fpylll default strategy，执行记录保留实际版本和策略摘要。

B 为 k=40、κ=0、d=216；E/D 为 k=40、κ=4、d=212。三组均从公开输入独立冷启动，独立建基、约化和必要预处理，不加载另一组的约化基或数据库。当前基行检查在整个冻结 schedule 后执行，不逐 tour 提前停止；因此 B 的成功是“β32 第二轮完成后检查得到”，不能称为已测得的最小成功 β。

公开 pattern 使用历史 `historical_sha256_shuffle_v1`：对 `pattern-primal-v1:10001:{index}` 做 SHA256，大端解释为 Random 种子，shuffle 原始 128 个坐标，取排序后的前 40 项为 P。T 取剩余坐标中最大的 4 项；前三组分别为 `[121,124,125,126]`、`[118,120,121,125]`、`[123,124,126,127]`。重复集合也保留计费，实际本轮没有重复。

D/E 每个建好的 pattern 生成全部 `3^4−1=80` 个非零三元尾部，顺序和外部 ID 稳定，batch_size=80。第 1、2 个 pattern 的 P/C/T、种子、候选、目标、ID 映射和原始基摘要逐项一致；第 1 个 pattern 的独立约化基摘要也完全相同，为 `d883f3f8157c213be9de4ff1eabb45b4b3da76ded23859567199f0750f42ded9`。第 2 个 pattern 未完成约化，没有伪造约化基摘要。

所有组开启相同的非零约化基行公开检查。E/D 的该分支把 T 补零再重构，若成功应记为零尾部 `basis_row`，不能归给 Slicer；本次 E/D 该分支没有返回有效解。零目标解码分支保持 skip。

每组预算 600 秒，清理预留 5 秒包含在其中，工作截止为原起点后 595 秒。外层 guard 的 0.2 秒清理预留也在这 5 秒内。整体预算 1920 秒，各组最多 3 个 pattern；没有单 pattern 重置预算。源代码、计划和输入在启动前冻结，[plan.json](plan.json)、[sources.json](sources.json) 和 [command.json](command.json) 提供具体配置。

## 事后覆盖诊断：已求得类的有效尾部没有进入前两批候选

全部在线实验结束后，以 **本轮 B 公开验证通过的输出**为 anchor，复用独立 offline 工具对 f/g 同时做正确的 negacyclic 带符号旋转，另外核查候选覆盖。没有读取私有 truth，也没有根据这些结果改变本轮的 pattern、尾部、阈值、顺序或停止规则。这不是与私有参考数组的分类，也不说明其他可能的有效短向量类。

| 公开 pattern index | B 所得类的兼容带符号代表数 | 零尾部 | 非零尾部／full80 覆盖数 | 实际运行 |
| --- | ---: | ---: | ---: | --- |
| 0 | 2 | 2 | 0／0 | B/E/D 均运行 |
| 1 | 2 | 2 | 0／0 | E/D 运行，约化超时 |
| 2 | 2 | 0 | 2／2 | 三组均未运行 |

两个带符号代表相差整体正负号，对应一个去掉全局符号后的兼容旋转。B 原输出在首个 T=[121,124,125,126] 上为 `[0,0,0,0]`。因此，虽然前两组 pattern 对已求得的这个有效类兼容，但**非零尾部候选策略没有覆盖它**；零尾部基行分支本可独立恢复该类，本次 E/D 的实际约化基行未找到。

这把“pattern 兼容”“非零尾部覆盖”和“实际解码成功”三个事件明确分开。第 3 个 pattern 的事后覆盖不能升级为已运行或已成功，也没有根据这个标签补跑。详见 [posthoc_recovered_class_coverage.json](posthoc_recovered_class_coverage.json)。因此，本轮的零成功同时包含候选覆盖限制，不能全部归因为 Babai 或 Slicer 的解码能力不足。

## D 的正常后端确实运行了什么

实际配置：投影维数 **40**（不是 κ=4，也不是 BKZ β=32），编译投影上限 64；DB4096、单线程、单 BDGL block、buckets=256、multi_hash=4、nrand=16、迭代上限 400，seed=10001。每个接受的投影组含 1 个原始条目和 15 个随机化条目；随机化重抽次数不可观测。

入口确实走 `grow_db(4096) → Siever.bdgl_sieve(blocks=1,buckets=256,check_saturation=False)`，不是 sample_database_only；`interface_test_mode=false`、`force_kernel_iterations=false`。当前包装字段名称为 bdgl2，但显式使用一个 block；固定后端按投影维数裁剪自动 block 数，40 维也只能用一个 block。本轮没有把字段名称写成实际两个 block。

预处理正常完成一次，实际数据库大小 4096；80 个外部目标形成 40 个带符号投影组，640 条目标 DB 条目。实际记录了一次 `RandomizedSlicer.bdgl_like_sieve` 正常调用，调用本身约 **0.000104 秒**，**实际内核迭代数为 0**，不是 400。C++ 中投影饱和判定在迭代体之前，满足当前停止条件即返回；统计 before/after 的迭代、替换及成功约化计数均未变化。这说明正常投影停止条件不能替代完整重构和公开验证成功。

整段解码 67.621676 秒包含目标投影、随机化插入、1280 次 Babai 提升、整数向量转换及检查等，不能称为内核迭代耗时。实际没有返回半径内完整向量，也没有可归给 Slicer 的成功。完整证据见 [D首个pattern原始结果](run/D-main-0/owner/attempt_000/result.json) 和 [independent_review.json](independent_review.json)。

后端对 ambient dimension 212 大于编译局部维数上限发出的 warning 保存在 stderr；本次实际局部投影 40≤64，后端维数检查、数据库构建、解码均正常返回，整数基保持不变，隐藏 LLL/BKZ 调用为 0。没有重编译后端。

## 监督、完整性与结论边界

沿用阶段 2D 的 outer session＋inner PG 监督器，PID/starttime 身份核验、定向 TERM／KILL、subreaper 回收和最终活动残留检查。三组均 `cleanup_verified=true`、`deadlines_satisfied=true`，所有已启动尝试的活动残留均为空。超时在原工作截止执行，未给新的宽限或预算；E/D 的正常第一尝试和被截断第二尝试都保留在原始目录。

RSS 指标为同一扫描汇总本 trial owner＋worker＋后代，再对时间取峰；10 ms 采样，排除外层 guard，包含内层监督逻辑。三个范围一致，分别为 97,021,952／98,635,776／142,508,032 bytes。RSS 为估计，非原子扫描，共享页可能重复计入；没有严格内存 enforcement，不使用历史 RUSAGE_CHILDREN。未观察到的主动 setsid 逃逸不在完整 containment 保证内，实际 worker 不脱离该 session。少量 guard 元数据 IO 为协作式实测计时，超限会取消资格，不声称实时操作系统保证。

为复刻历史公开采样及保留中途超时证据，仅作必要比较层接入：新增 `patterns.py`，修改 `standalone.py` 的可选 pattern 规则；给 `reduction.py` 和 `standalone_worker.py` 添加逐 LLL/tour 开始／完成及精确证明的耐久遥测，不更改数值算法或 schedule。修改前文件保存在 [source_before](source_before)，新增两个针对性测试文件。运行前自动化 **239 通过，0 失败／错误／跳过**，实际主参数 batch 只启动一次。

[posthoc_validation.json](posthoc_validation.json) 对公开候选、来源、进度、配对摘要、执行前缀、预算及清理做独立核查，全部通过；1888 个受保护文件和启动前 237 个冻结源码／运行时／输入摘要一致。私有参考文件只核对元数据，未读内容。阶段 1、2A—2D、封存求解器、后端和历史原始结果保留；未 reset、clean、stash、提交或 push。

事后汇总曾将“第二次尝试未完成”保守写成 Slicer 总调用数 unknown，现按方法和耐久阶段前缀修正为 B/E/D=0/0/1，未改真实结果或成功资格。修正前的 JSON／CSV 保存在 `actual_results.before_call_count_fix.*`。

本次固定配置下，只有 pattern primal B 恢复了公开有效解；正常 hybrid＋Babai 和 hybrid＋Slicer 没有成功，尚未观察到完整方法或 Slicer 的收益。前两批非零尾部列表没有覆盖 B 所得有效类，且 D 本次没有进入实际内核迭代；不能由此判断 Slicer 在有效尾部覆盖、充分迭代下的表现。本轮按要求结束，不扩大参数网格，不补跑第三个 pattern，不因失败追加试验。
